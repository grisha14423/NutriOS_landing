**# Руководство по работе с репозиторием**

**## Структура проекта и организация модулей**

Это Vite-приложение на React 19 — landing page для NutriOS. Точкой входа приложения является `src/main.jsx`; он монтирует `src/pages/NutriOSLandingPage.jsx`. Секции landing page следует размещать в `src/components/landing/` (например, `Hero.jsx` и `SafetySection.jsx`), общий текст и данные для отображения — в `src/data/landingContent.js`, а глобальные стили landing page — в `src/styles/landing.css`. Результат production-сборки генерируется в `dist/` и не должен редактироваться вручную. Файл `SPEC.md` определяет требования к продукту, доступности, безопасности и адаптивному дизайну.

**## Команды для сборки, тестирования и разработки**

- `npm install` устанавливает зафиксированный набор зависимостей из `package-lock.json`.

- `npm run dev` запускает локальный сервер разработки Vite.

- `npm run build` создаёт production-сборку в `dist/`; выполняйте эту команду перед передачей UI-изменений.

- `npm run preview` запускает собранное приложение для локальной проверки в условиях, близких к production.

Автоматические тесты и скрипт линтинга в настоящее время не настроены. Проверяйте изменения с помощью `npm run build`, а также вручную проверяйте desktop- и mobile-версии в браузере.

**## Стиль кода и соглашения об именовании**

Используйте ES-модули и функциональные React-компоненты. Соблюдайте существующий стиль: два пробела для отступов, одинарные кавычки, отсутствие точек с запятой и завершающие запятые в многострочном JSX. Файлы компонентов и экспортируемые компоненты называйте в PascalCase (`SectionHeading.jsx`); для функций, props и полей данных используйте camelCase. Разметку, относящуюся к конкретной секции, держите рядом с соответствующим компонентом, а переиспользуемый текст и повторяющиеся данные карточек централизуйте в `landingContent.js`. Используйте понятные имена CSS-классов, относящиеся к landing page.

**## Тестирование и UI-проверки**

При изменении компонента проверяйте его якоря секций и работу CTA, а также доступность с клавиатуры. Сохраняйте адаптивные breakpoint'ы, указанные в спецификации, и не добавляйте фиксированную высоту секций, которая может обрезать переведённый текст. Продукт предназначен только для wellness/образовательных целей: не добавляйте заявления о диагностике, лечении или медицинских результатах. Следите за тем, чтобы demo-контролы оставались явно локальными демонстрациями и при необходимости сообщали динамические изменения вспомогательным технологиям.

**## Правила для коммитов и Pull Request**

В этом workspace нет доступной истории Git, поэтому используйте краткие императивные названия коммитов, например `Add mobile spacing to hero`. Коммиты должны быть сфокусированы на одной задаче. Pull Request должен содержать описание пользовательского изменения, ссылку на соответствующую задачу, если она есть, список выполненных проверок (`npm run build`) и скриншоты до/после для визуальных изменений. Отдельно отмечайте любые изменения, касающиеся маршрутизации CTA, доступности или wellness/safety-текста.
